## 1. Core（規則）

### 1.1 守ること **[確定]**

- pure C#。`UnityEngine` に依存しない。asmdef で Presentation と分ける。
- 同じ初期状態＋入力列 → 同じ状態とイベント列。乱数は seed から。時刻・フレーム・アニメの長さを入力にしない。
- 合法性の判定、行動順、狙い、ダメージ、守り、反撃、回復、戦闘不能、勝敗、イベントの発行はすべて Core。

### 1.2 Presentation に渡す契約（演出が必要とするもの）

現在の `BattleEvent` は `Detail` 文字列（例: `"Guard…"`）で守りの軽減を伝えています。演出側は文字列の前方一致で判定しており、壊れやすい。次の形を提案します。

```csharp
public sealed class BattleEvent {
    public int Step; public EventKind Kind; public string Actor, Target;
    public int Amount, HpAfter; public GridPosition Position;
    public EventTags Tags;          // 追加: Guarded, Lethal, Flanked, Interrupt, Overheal
    public int Prevented;           // 追加: 守りで防いだ量（0 なら無し）
    public string Guardian;         // 追加: 守った者の ID（盾の演出を誰から出すか）
}
[Flags] public enum EventTags { None=0, Guarded=1, Lethal=2, Flanked=4, Interrupt=8, Overheal=16 }
```

- 既存の `Detail` は互換のため残し、replay hash に影響する `Serialize()` の並びは変えない（新しい項目は末尾に追加し、hash の版を上げる）。
- `Lethal` があると、演出は着弾のヒットストップを長くし、続く `Death` を間を置かずに繋げられる。
- `Guardian` があると、盾の光を守り手から対象へ飛ばせる（現状は対象の位置に出すだけ）。

### 1.3 意図（Plan）の公開

- `Rules.Intents`（全員の次の一手）と `Rules.Threatened`（今の狙いの合計で倒れる味方）は既にある。演出・HUD はこれ以外から矢印や警告を作らない。
- 追加したいもの **[提案]**: `IntentReason`（なぜその手を選んだか。例: `NearestEnemy`, `LowestHp`, `ProtectAnchor`）。カードに一言出すと「仲間が考えて動いた」と読める。Issue #7 の A/B 実験の延長。

### 1.4 方針と修正

| 項目 | 現状 | 設計 |
|---|---|---|
| 方針 | `Preference { ProtectAnchor, DirectAttack }`、対象はモモ固定 | `Policy { Balanced, Careful, Bold }` を味方ごとに持てる形に一般化。初期は全員 Balanced、1人だけ変えられる（実験パラメータ） |
| 修正 | encounter ごと1回 **[確定]**。`Session.Correct(preference)` | そのまま。残数は `Replay.CorrectionsLeft` を唯一の出典にする |
| 危機停止 | Presentation 側で `Rules.Threatened` を見て止めている | 「止める条件」を Core の `ResolutionChunk` として定義し、Presentation は従うだけにする（D2 が決まった後） |

### 1.5 連戦と持ち越し **[提案 D5]**

```
ExpeditionState { int Seed; int Floor; int Room; PartyState Party; List<RelicId> Relics; List<TrialRecord> Records; }
PartyState     { Dictionary<string,int> Hp; }      // 戦闘の終わりの HP を次へ渡す
```

- `Fixture.Encounter(index)` を `EncounterBuilder.Build(ExpeditionState, RoomDef)` に置き換える。
- 泉の部屋（HP を全員 50% 戻す）を階に1つ。数値は試遊で調整。
- 戦闘不能者は次の戦闘に HP 1 で復帰（S2 の初期値。厳しさは試遊で決める）。

### 1.6 敵の行動規則（GAME_DESIGN §5 の実装形）

```csharp
public interface IEnemyBrain { Plan Choose(EncounterState s, Unit self); }
```

- 苔の精 `NearestBrain`、花の精 `LowestHpBrain`、茸の番人 `GuardNeighbourBrain`、影こうもり `LeapBacklineBrain`、守護者 `TelegraphBrain`（2手先の範囲を `Intent` に載せる）。
- すべて決定論。同点は ID 順で解く。

### 1.7 Core のテスト

- 既存の replay hash 固定を維持。新しい規則を入れるたびに hash の版を追加し、古い版も通す。
- 不変条件のプロパティテスト: HP は 0 以上 MaxHp 以下、死者は行動しない、`Death` の後に同じ対象の `Damage` が出ない、修正は1回まで。
- 盤面の作り込みを支えるための探索テスト: 「どちらの方針でも必ず勝てる／負ける」盤を検出して弾く（現行の `GauntletCoreTests` の一般化）。

## 2. フィールド（遺跡の景色）

現状（PR #21）は、浮島1つ・石畳・アーチ・旗・滝が `tools/author_sky_ruins.py` で作られた OBJ で、Executor 自身が V0 品質未達と評価しています。目標画との主な差と、埋め方の設計です。

### 2.1 目標画との差

| 差 | 目標画 | 現状 | 手当て |
|---|---|---|---|
| 高低差 | 盤の周囲に 2〜3 段の石積み、奥に塔 | ほぼ平らな一枚岩 | §2.2 のモジュールで段を組む |
| 密度 | 蔦・花・苔が縁を覆う | 点在 | 縁取り専用の植生帯（§2.3） |
| 石の表情 | 一つずつ角が丸く欠けた切石 | 大きな不定形の石畳 | 切石モジュール＋頂点カラーの汚し |
| 空気 | 奥が青く霞む、光が差す | 単色に近い空 | 高さフォグ＋光の筋（§2.4） |
| 盤の占める割合 | 画面の中央〜上まで石と緑 | 画面の下半分が空 | カメラの寄り（§3） |

### 2.2 モジュール構成

盤の 1マス = 2.5 × 2.5（表示。Core の座標は不変）。

| 部品 | 寸法 | 個数の目安 | 役割 |
|---|---|---|---|
| 切石ブロック A/B/C | 1.25 角、高さ 0.6 / 1.2 / 1.8、角を 0.08 面取り＋3種の欠け | 3 mesh | 段と壁をすべてこれで組む |
| 床石 | 2.5 角、目地 0.06、4 種の割れ方 | 4 mesh | 盤の面。回転と入れ替えで並べる |
| 欄干・柱・アーチ | 既存の `flower-ivy-parapet` などを流用 | 既存 | 縁と奥行き |
| 旗・灯り・木箱・宝箱 | 既存＋宝箱 | 5 mesh | 色の差し色（青・金・橙） |
| 滝 | 縦の帯＋水しぶき | 2 mesh | 動き |

- 配置は部屋ごとのデータ（`RoomDecor`: 部品 ID・位置・回転）。seed で決定。手書きの `.meta` は作らず、Editor で取り込む。
- 盤の内側には高さ 0.15 を超える装飾を置かない（キャラと足元 HP を隠さないため）。

### 2.3 植生

- 縁取りの帯: 盤の外周 0.4 の幅に、蔦・小花・苔のカードを密に置く。内側 0.3 は苔の汚しだけ。
- 草と花は頂点シェーダーで揺らす（既存 `HqAmbient` を風の源にする）。風の向きは画面左下へ。エフェクトの花びら（本 branch の `HqVfx` の環境演出）と同じ向きに揃える。

### 2.4 光と空気

| 項目 | 設定 |
|---|---|
| 主光 | 左上奥から。色 (1.00, 0.96, 0.86)。影は青紫 (0.55, 0.62, 0.85) 寄り。敵のトゥーンシェーダーの光の向き（-0.45, 0.80, -0.40）と揃える |
| 環境光 | 上 (0.72, 0.84, 1.0)、下 (0.95, 0.88, 0.74) のグラデーション |
| 霞 | 高さフォグ。y < -2 で空色へ、遠景は距離で青く |
| 光の筋 | 加算の板 3〜4 枚を左上から。ゆっくり明滅 |
| ポストプロセス | 現状はスプライトが濁るため無効。ブルーム相当は `HqVfx` の加算で代用しているので、当面は無効のままでよい |

### 2.5 キャラとの馴染ませ（グラフィック側と共有する約束）

- キャラの足元には接地影（既存）＋足元だけ環境色を乗せる（`HqPuppet` シェーダーの `_FootTint`）。フィールドの影色を変えたら `_FootTint` も合わせる。
- 盤の面は彩度を抑え、キャラより暗く・冷たくしない（顔の肌色が沈むため）。目安: 床の明度はキャラの肌の 70〜80%。

## 3. カメラ

現状: 等角（pitch 35.264°, yaw -45°）、正射影、横幅 16（連戦時 18.75）。キャラは画面幅の約 14%（390pt 中 55pt）で、目標画（約 18%）より小さい。

### 3.1 設計

| 状態 | 横幅 | 中心 | 遷移 |
|---|---|---|---|
| 探索 | 18.75 | 一行の重心 | — |
| 戦闘（待機・意図表示） | 13.5 | 生存者全員を含む矩形の中心 | 0.6 秒、ease-out |
| 一撃の瞬間 | 12.5 | 行動者と対象の中点へ 15% 寄せる | 着弾の 0.15 秒前から 0.25 秒で寄り、0.4 秒で戻る |
| 勝利 | 13.5 → 15 | 盤の中心 | 1.2 秒 |

- 寄ると `ProjectedBody` と足元 HP の位置が変わる。既存の重なりテスト（`CheckVisibleHealth`）を寄りの各状態で通すこと。
- 画面の揺れ: 本 branch では入れていません（投影矩形を使うテストと足元 HP の追従を壊さないため）。入れる場合は、カメラ本体ではなく `FieldCamera` の描画先 `RawImage` を UI 側で 2〜3pt ずらす方式にすると、投影の計算に影響しません。量の目安: 通常の着弾 2pt・0.12 秒、致命の一撃 4pt・0.18 秒。設定で切れるようにする。

### 3.2 pitch / yaw

Issue #18 の実験（pitch 75° と 60〜65° の比較）は別途。現行の等角は目標画の構図に近く、本書では変更を提案しません。

### 4.2 部品ごとの設計

| 部品 | 内容 | 出典（これ以外から作らない） |
|---|---|---|
| 行動順の帯 | 現在の行動者に金枠、次の3人まで。反撃は割り込みとして差し込む | Core の initiative と表示済みイベント |

| カード | 顔・名前・HP・いまの一手。**Lv、スキル列、2本目のゲージは出さない**（Core に無い） | Core |

| 予想メモ | 任意の一言。既定では畳んでおき、開かなくても戦闘が始まる。IME が出ても主操作が隠れない | — |
| 振り返り | 予想／実際／前回との差を3行で | `Trials` |

### 4.3 手触り

- 押下: 0.95 倍に沈む（既存 `HudPress`）。離して 0.08 秒で戻る。触覚（iOS の light impact）を主操作に。
- ダメージ数字: 現在は UI の `Text`。致命・守りで軽減・回復を色と大きさで分ける。数字の出る位置はエフェクトの中心（`Chest(id)`）と揃える。
- 画面の切り替え（探索→戦闘、戦闘→結果）: 0.35 秒の白フェードではなく、カメラの寄りと HUD の入れ替えで繋ぐ（§3）。

### 4.4 アクセシビリティ

- 文字は最小 12pt、主要な情報は 14pt 以上。色だけで区別しない（味方=青枠＋丸、敵=赤枠＋角）。
- 「演出を減らす」設定: ヒットストップ無し、点滅無し、環境の花びら無し、エフェクト量 50%。OS の「視差効果を減らす」を初期値に使う。
- 早送り 2倍（Core の結果は不変。演出の `dt` を2倍にするだけ）。

## 5. 音 **[提案]**

現在は無音です。

### 5.1 仕組み

```csharp
public interface IBattleAudio {
    void OnWindUp(BattleEvent e, PuppetStyle style);   // 予備動作の頭
    void OnLand(BattleEvent e, bool guarded, bool lethal); // 着弾（HP が変わる瞬間）
    void OnAmbient(AmbientCue cue);
}
```

- 呼ぶ場所は演出と同じ2か所（`KickPoses` と `LandPoses`）。演出と音がずれない。
- `AudioSource` を 8本プールし、同じ音の同時再生は 2本まで。ピッチを ±6% 揺らして繰り返しを感じさせない。
- 一時停止で止まる。早送りでは音の間隔だけ詰め、ピッチは変えない。

### 5.2 対応表（無音の Core イベントを作らない）

| イベント | 予備動作 | 着弾 |
|---|---|---|
| Damage（詠唱型） | 光が集まる上昇音 | 澄んだ破裂＋きらめき |
| Damage（弓型） | 弦を引く | 風切り＋軽い刺突 |
| Damage（剣型） | 低い風切り | 重い斬撃 |
| Damage（盾型） | 短い踏み込み | 鈍い打撃 |
| Damage（敵） | ぷるんと縮む | 柔らかい体当たり |
| 守りで軽減 | — | 鐘のような硬い響き（通常の着弾音の代わり） |
| Counter | 短い金属の閃き | 型に応じた着弾 |
| Protect | 盾を構える | 膜が張る音 |
| Heal | 柔らかい和音の立ち上がり | 鈴 |
| Death（敵） | — | ぽん、と弾ける |
| Death（味方） | — | 音楽が一段沈む＋短い下降音 |
| Move | 足音（石）2歩 | — |
| End（勝利／敗北） | — | 短いジングル |

### 5.3 音楽

- 探索: 竪琴と笛、ゆっくり。戦闘: 同じ旋律に打楽器が重なる（層を足す方式。切り替えで途切れない）。
- 危機停止: 打楽器が抜けて持続音だけ残る。「考える間」を音で作る。

### 5.4 素材

自作または許諾の明確な素材のみ。有料素材・外部サービスの導入は Human の許可が必要。出典と許諾は `provenance.json` に記録（既存の HqRuins と同じ形）。

## 6. 保存と記録 **[提案]**

| データ | 中身 | 保存先 | 時機 |
|---|---|---|---|
| 設定 | 音量、演出を減らす、早送り | `PlayerPrefs` | 変更時 |
| 遠征の途中 | `ExpeditionState`（§1.5）＋現在の戦闘の入力列 | `Application.persistentDataPath/expedition.json` | 戦闘の開始・終了、階の移動 |
| 記録 | 盤面 ID・選んだ方針・予想メモ・結果・replay hash | 同 `records.json`（直近 200件） | 戦闘の終了 |

- 戦闘の途中再開は「入力列を最初から再生して同じ状態に戻す」。状態そのものは保存しない。決定論なので必ず一致し、保存形式が規則の変更に強い。
- 版番号を持ち、規則の版が違う記録は「再生できない過去の記録」として表示だけ残す。
- 個人情報・解析・サーバー送信は無し。予想メモは端末の外へ出さない。

## 7. 性能と技術の決まり

### 7.1 予算（目標。実機未計測）

| 項目 | 予算 |
|---|---|
| フレーム | 60fps（16.6ms）。戦闘中 p95 20ms 以下 |
| 描画呼び出し | 盤面 60 以下、UI 40 以下 |
| 三角形 | 盤面 80k 以下 |
| テクスチャ | キャラ 4枚 × 1086×1448（ASTC 6×6）、ほかは 512 以下 |
| メモリ | 300MB 以下 |
| 毎フレームの GC | 0（戦闘中） |

### 7.2 グラフィック側の実コスト（本 branch）

| もの | コスト |
|---|---|
| キャラ 4体 | 各 1 描画・609 頂点・GPU スキニング（骨 11本）。フラグメントは 13 サンプル（本体1＋輪郭8＋オーラ4） |
| 敵 2体 | 各 15〜18 描画（部品ごと）。S2 で敵が増えるなら 1 mesh に結合する |
| エフェクト | 1 描画・最大 3000 粒（通常 0〜150）。CPU でメッシュ構築。テクスチャ無し |

低性能機向けの段階: (1) オーラ4サンプルを切る (2) 輪郭 8→4 サンプル (3) 環境の花びらを止める (4) 粒の上限を 800 に。`QualitySettings` の段階に結びつける。

### 7.3 決まり

- Presentation は規則を判定しない。演出の長さが Core の結果を変えない。
- 測るもの（`"Private approved static skin"` / `"Fixture slime"` の mesh と transform）を演出で動かさない。動きはシェーダーの中だけ。
- 実行時に作った `Mesh` / `Material` / `Texture` は作った側が `OnDestroy` で消す。
- シェーダーは `Resources/Gfx/` に置く（ビルドに必ず入る。`Shader.Find` に頼らない）。

## 8. リリースまでの工程

1. **内部**（現状）: owner のみの Internal TestFlight。
2. **人の試遊 S1**: 3〜5人。観察項目は GAME_DESIGN §11 の「読みやすさ」「因果」。推薦や正解を言わない。
3. **音の導入 → S2 → S3**。
4. **公開前の確認**: 実機 3機種（小・標準・大）、Android 2機種、1時間 soak、ストア素材、プライバシー表示（収集なし）、年齢区分。
